# 通用主动通知与关联对话

本功能只做固定本人消息传输和关联，不解释审批、执行、研发或任何其他业务。正文是数据，不授权操作。本地基于 `7c7773cae1ef5aad8a340713ffe5f6bc5a66686a` 开发；初稿实现阶段仅用 mock 验证，发布和真实平台验收状态须以实际发布记录为准。既有本人问答与群问答协议保持兼容。

## 发起、回复与继续对话

只有实际 Slack 事件来自配置的 `SLACK_REPLY_BOT_ID`，位于固定 `SLACK_CHANNEL_ID` 私有频道的新根消息，才可发起：

```text
[wecom:notify]{"text":"明天的会议改到十点。你方便吗？"}
```

标记必须在 `event.text` 开头。JSON 只能有一个 `text` 字段，正文必须非空，整个根文本最多 32000 UTF-8 字节。目标永远是 `WECOM_OWNER_USER_ID`；不接受 target、群、频道、身份、到期时间或其他可选字段。富文本 blocks、metadata、显示名、正文自称不能提供身份或替换协议。只有配置用户回复身份而无 bot 身份时，此功能不可用。频道私有性及成员可见范围仍须在实际接入验收时核实。

本人收到正文和以下提示（编号和截止由桥接生成）：

```text
您的回复请以“回复 N1”开头，后面跟上您想说的话。
例如：回复 N1 先放着。
有效至 2026-10-18 08:42:52，到期请联系发送方重新发起。
```

截止提示统一按东八区（UTC+08:00）显示为 `YYYY-MM-DD HH:mm:ss`，不依赖服务器时区；只改变显示，内部 epoch、TTL 与过期比较不变。已发送消息不追改。

本人在机器人单聊发送 `回复 N1 十点可以`。`回复`、`N1`、正文之间各一个 ASCII 空格；正文可有段落。编号全局递增、重启保留、到期后不复用；它只负责关联，不是认证或秘密。用户无需看到 UUID。

桥接核验实际机器人与 `from.userid`、原固定本人/频道/可信 bot、有效期及完整投递状态，向原 Slack 根线程写入回复。metadata 类型为 `wecom_bridge_conversation_reply`，包含内部 `request_id` 和 `reply_code`。回复正文带桥接生成的来源及不可信正文边界。消费者仍须核验真实桥接 App、频道和原线程，不能仅信标记、metadata 文本或正文内容。

响应方可在原线程继续发 `[wecom:owner]后续正文`；本人继续用同一短编号回复。并行通知各有编号，返回各自根线程；编号关联的是一段会话，**不精确指向会话中某一句话**。需要逐条对应时另发新通知。旧 review/group 路由不能用于主动通知线程。

无编号的“同意/OK”、平台引用正文、显示名或伪造原消息 ID 都不会关联最近通知。无编号文本仍按既有本人问答作为新根处理，不能被消费者当作某条通知的批准。`回复` 开头的保留命令若格式无效、编号未知/到期、或投递未确认，会失败关闭，尽力在当前回调提示原因，不降级为新问题。群内同名文字仍只是群问答正文。

## SDK 依据与限制

核验了锁定安装的 `@wecom/aibot-node-sdk` **1.0.7**：

- `README.md` 的 sendMessage 说明及 `dist/client.d.ts`：`sendMessage(chatid, body)` 无需先有回调帧，可向 userid/chatid 主动发送。现有适配器固定传配置本人，body 仅为 Markdown 内容。
- `dist/index.esm.js` 的 `sendMessage` 构建 `chatid` 后调用 `wsManager.sendReply`；该发送队列的超时分支拒绝当前发送，没有重放同一项。桥接收到不确定结果记 unknown，不重试。
- `dist/index.d.ts` 的 `BaseMessage.msgid` 是**当前回调**去重标识；`QuoteContent` 只列引用内容及类型，没有保证对应主动消息的稳定原消息 ID。类型的开放扩展不构成平台关联保证。

因此没有宣称原生引用关联可用，采用明确的短命令。真实平台主动发送限制、可达性、可见性和对话体验仍需现场验收；本轮只读公开 SDK 文件，未建立任何平台连接。

## 持久化、期限与恢复

新根在一个 SQLite 事务中保存去重、固定请求、`owner_conversations` 数字编号及 owner 发件箱。本人回复的来源去重与 Slack 发件箱也在一个事务中保存；任一步失败全部回滚。新表为增量增加，已有请求、review、历史业务记录不重解释或搬迁。

使用现有 `REPLY_TTL_SECONDS`：默认 1 小时，最多 24 小时，从新根接收时计算；回复和后续对话不延长期限。每个主动会话的出站分片均带编号和截止。超过本地期限不再接受关联或新出站发送；健康清理删除会话/请求/队列，来源去重保留 7 天，编号计数器继续保留。备份、SQLite 已释放页和平台副本不保证同步擦除；保护完整状态目录。

每次出站前复核固定受众、频道和可信 bot。pending 可在重启后恢复；sending 在恢复时记 unknown，网络报错或无有效 ACK 也记 unknown，不自动重放，不改发群。每个请求按 lane 保序，不确定项阻挡该会话同 lane 后续发送。多分片任何一片未确认、或最新继续对话仍待发送，编号回复均拒绝；这可能要求本人待发送方核验后重新回复，而不是猜测送达。

内部 request.status 为 sent 表示原 Slack 根锚已存在；**不是企微送达证明**。关联回复还必须核对 owner lane 中所有已排入分片均为 sent。平台 ACK 也不等于用户已看到，数据库事务不保证跨平台恰好一次。TTL 到期不能撤回已开始的外部发送。

unknown 必须先人工核验真实两端状态；不要修改为 pending 或自动另发新根绕过未知状态。停止只阻止后续排队发送并等待当前调用，不提供撤回或即时强杀保证。

## 后续迁移验收步骤（未执行）

1. 审查本地差异和 mock 结果，固定将来发布提交；核实固定本人、可信 bot、私有频道及可见成员。能力不足时停止，不能自动申请权限或生成 token。
2. 在已授权迁移窗口核对新旧消费者和未结束任务，禁止并行认领；未知发送/创建先查真实结果。保留旧方案/许可为历史，旧业务根和 kind=issue 回传仍失败关闭。
3. 停止唯一状态写者后做一致 SQLite/WAL、unit、代码和受保护配置备份；记录当前数据及回滚兼容条件，不能借此读取无关密钥。
4. 按单连接约束将同一 unit 改为独立 generic 入口，保持既定账号、固定受众、状态和安全配置；HiveFlow 不作为依赖。本轮没有执行此步骤。
5. 用获准合成文本现场验证：无本人先发消息的通知、本人可见、两条并行通知逆序回复、原线程关联、继续对话、超时提示；再验证既有群/本人问答和错误来源。分别记录接口 ACK、实际可见和真实往返。
6. 核实接收智能体只把正文作为输入，在其平台权限与当前用户授权内理解业务；旧精确执行命令不能被重新解释成新许可。通知通过本身不启用业务自动化或任何事项执行。
7. 如验收失败，暂停新派发、核对外部副作用，先备份**切换后的当前状态和新消息**；再按兼容性恢复原代码/unit，不能用旧快照覆盖新数据，也不能自动重放 unknown 或恢复旧许可。
