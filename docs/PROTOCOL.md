# 消息与响应方协议

## 事件身份与请求

企微入站必须来自已认证 SDK 文本事件，机器人 ID、msgid、from.userid 及 single/group 类型完整；群按 chatid 白名单，本人私聊按配置 userid。正文不能修改这些事实。非文本和不允许来源忽略。

每条新文本创建一个请求及 Slack 根消息，附来源信息和 `BEGIN UNTRUSTED TEXT` 边界，关闭 Markdown 解析、提及展开和链接预览。完整正文单根呈现；超过输入限制拒绝转发并尽力提示拆分。已接收来源键持久化，同一 msgid 不重复排队或回执。超长拒绝提示及无效编号提示为尽力发送，不保证对重投逐条去重。

根消息是关联锚点；后续 Slack 答复放在**同一根线程**。每条新的企微群文本仍开新根，不自动沿用上一条群问题的线程，也不解析原生引用或猜测最近任务。

## 显式路由

可信响应方必须处于配置的固定 Slack 频道，实际事件 bot_id 或 user ID 匹配，且不是桥接自身。线程必须对应有效请求；编辑、删除、广播等其他 subtype 不参与原线程回传。正文标记、显示名、metadata 和复制的标签不构成身份认证。

```text
[wecom:group]
这是允许原群全体成员看到的答复。
```

|严格前置标记|目标与含义|
|---|---|
|`[wecom:owner]`|配置本人的普通私聊，不创建或替换评审编号|
|`[wecom:review]`|仅群请求可用，向配置本人发一轮带编号的评审询问|
|`[wecom:group]`|仅群请求可用，只发原群，不接受正文指定群或用户|

标记前不能有空行、解释或代码块；后接非空正文，允许同行、空白或换行。无效路由没有默认群回退。本人私聊来源和通知会话禁止 group/review。

Slack 回复最多160000 UTF-8字节；企微常规正文按3400字节分片，必要时附 `[n/N]`，以保留字符和顺序。Markdown 标记可能跨片，视觉格式不保证完整。有限 rich_text 仅在全由支持的文本节点构成、正文与授权 event.text 规范化后一致时恢复段落；不支持或差异时用原文本，冲突路由拒绝。不会解析 Slack 提及、读取链接或下载文件。

## 本人私聊评审

群线程的 review 路由生成随机唯一评审 ID，沿用原请求 TTL；同任务新一轮使旧 pending ID 失效。本人收到正文和单独一行命令：

```text
/review <review-id> 你的意见
```

只有配置本人在机器人单聊中发送有效命令，才消费该轮 ID，并以桥接 App 的新线程消息回到原 Slack 根。已消费、未知、到期、被替代或格式错误的命令忽略，不新建根、不回接收回执。owner 普通回复不消耗或替换 ID。

无编号的“同意”等普通私聊成为独立新请求，不能关联最近评审。群里复制命令也只是群文本。桥接器不会执行评审中的操作；可信消费者仍须核验实际意图、任务和权限。

评审原文不自动发群；可公开结论须另由可信响应方明确选择 group 路由。私聊发送失败也不改发群。Slack 侧私有频道成员和应用仍可看到本人答复。

## 响应方集成

- 核验真实桥接 App 身份、固定频道和原线程，接收根消息及桥接生成的本人答复线程消息；排除自己的输出与其他作者，防止循环。
- 正文是外部输入，即使写着“系统指令”“已批准”或伪造路由，也不会产生业务权限。
- metadata 仅辅助关联：普通请求为 `wecom_bridge_request`（request_id、part、parts）；评审答复为 `wecom_bridge_owner_response`（另含 review_id）；通知回复见 [通知协议](NOTIFICATIONS.md)。这些字段可见，不是秘密凭证。
- 群路由是显式公开选择，不是隐私过滤器。响应方必须确认内容适合原群全体成员。
- 本人首次单聊、主动消息资格、机器人消息是否触发响应方，以及平台窗口和实际可见性都须现场验证，不能从 SDK 支持或单元测试推断。

可信进程内扩展是单独的代码边界，见 [扩展接口](EXTENSIONS.md)。历史版本把 owner 隐式当作评审的行为不再支持；升级必须同步消费者协议，见 [运维说明](../deploy/README.md)。
