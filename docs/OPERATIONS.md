# 可靠性、观察与排障

## 发件箱与期限

|状态|含义与处理|
|---|---|
|pending|本地已排队，尚未开始外部调用；有效期内、原身份与固定目标仍合规时可恢复|
|sending|调用意图已落盘；崩溃后改为 unknown，不自动再发|
|sent|平台返回预期 ACK；已清除该 job 的正文，不代表用户已经阅读|
|unknown|调用报错/ACK 不满足预期、ACK 后本地保存失败，或发送前载荷/授权校验失败；停止该请求同 lane 后续项，人工查证|
|expired|未开始发送就已过期，不继续投递|
|quarantined|旧状态缺少可信来源，保持隔离，不转换为新路由|

owner 与 review 共用同一请求的 owner lane；group 和 Slack lane 独立。某请求同 lane 的前项未确认会阻塞其后项，不改变目标绕过失败；其他请求仍可处理。损坏 JSON 或缺正文的 job 记为 unknown（stage=payload），不会阻塞整轮队列，也不会把坏载荷写进日志。

请求映射、评审、普通通知与队列按本地 TTL 清理，去重来源保留7天。健康循环每30秒清理并推动队列；断开企微时仅暂缓企微出站，已授权 Slack 投递可以继续。恢复只处理仍有效的 pending；不会复活 consumed、unknown 或到期项。

TTL 是本地界限，不是平台投递资格。等待节流后再次检查期限、停止状态和企微连接状态；不会因此延长有效期。已经开始的网络调用不能靠 TTL 或停止命令撤回。清理、已释放 SQLite 页、WAL、备份和两端平台副本不是安全擦除机制。

### 节流与吞吐

Slack 出站全局至少间隔约1.1秒。企微**主动出站队列**全局至少间隔约4秒，长消息每片分别计算；多个目标也共用该队列，因此长回复和排队会增加等待时间，可能在发送前过期。进程重启不恢复节流时钟。

[企微官方长连接文档](https://developer.work.weixin.qq.com/document/path/101463)说明回复与主动推送共享每会话30条/分钟、1000条/小时限制；主动发送还要求用户曾在相应会话给机器人发消息。即时回执/拒绝提示不经过主动队列节流，也可能消耗平台额度；4秒间隔是保守降速，不保证总体永不触限。平台限制或共享额度变化仍以实际返回与人工验收为准。

发送调用报错（包括限流）按 unknown 保守处理，不自动补发。不要靠扩权限、换机器人连接或手动改状态绕过不确定结果。

## 日志

运行时输出 JSON，SDK 原始日志关闭。不打印 token、消息正文、完整事件、签名 URL、Slack 频道 ID 或企微用户/群 ID。request 为桥接内部随机关联 ID；它也应只在获准的排障范围使用。

|事件|含义|
|---|---|
|`bridge_started`|启动流程完成；不是两端真实往返通过|
|`wecom_authenticated` / `wecom_disconnected` / `wecom_reconnecting`|认证/连接变化，重连期间不当作可发送|
|`request_queued`|本地入站与发件箱事务已提交|
|`delivery_sent`|本次方向的预期平台 ACK 已确认|
|`delivery_unknown`|按 request/direction 核对；stage 为 payload、authorization、transport、acknowledgment 或 persistence，不含平台错误原文|
|`wecom_ack_failed`|即时回执尽力发送失败；不重发已接收请求|
|`health`|企微连接状态及各 job 状态计数；不证明 Slack 响应方在线|
|`startup_failed`|config/state/application/connect/identity 阶段失败，检查本地受控配置|
|`queue_error` / `wecom_ingress_error` / `slack_error` / `wecom_error`|组件失败类别，不能仅凭日志猜测底层原因|
|`wecom_replaced_connection`|连接被替代，退出78，先找重复实例|

没有公开健康端口、HTTP 管理接口、自动重试按钮或强制释放锁工具。需要更详细证据时，只在授权范围检查平台状态与脱敏数据；不要在生产开启 SDK 原始调试日志。

## 常见问题

|现象|先核对|不要这样做|
|---|---|---|
|配置检查失败/退出78|缺失字段、回复身份恰选一个、状态权限、重复实例；检查日志阶段|输出 .env 或令牌、无限重启|
|有回执，没有 Slack 请求|request_queued、Slack 方向状态、频道/App 成员和权限|认为回执等于下游完成、盲重问大量消息|
|Slack 有答案但未回传|实际作者、固定频道、原 thread_ts、严格前置标记、非空文本、TTL|按显示名放行、把私聊降级发群|
|unknown 增长|阶段、时间、两端实际消息与唯一请求关联；必要时暂停新派发|改回 pending、删除去重库或重放整批|
|通知编号不能回复|本人单聊身份、格式、固定 bot/频道、TTL、所有 owner 分片是否确认|猜最近通知或用无编号“同意”关联|
|长回复慢/过期|4秒主动队列间隔、队列前项、剩余 TTL、平台限额|缩短安全等待以冲击限额或无审核延长期限|
|授权群无入站|群 chatid、机器人是否收到 text、平台 @ 与投递配置|假定未 @ 文本一定投递、扩大到全群采集|
|被其他连接踢下线|同一 Bot ID 是否在另一进程/主机运行|启动第二个 bot 客户端“测试”|

## 停止与恢复

SIGTERM/SIGINT 停止新的入站和后续队列发送，短暂等待当前调用；运行时最多等待约15秒，systemd 模板外层停止上限30秒。外部调用可能已经发生，强停不能撤回消息。

unknown 先核对真实两端结果；不能通过改数据库、重建根消息、清库或恢复旧快照自动重放。无法确认时保持隔离，由相关人员决定是否发起新的独立询问，并接受重复风险。程序没有“确认未送达后自动重试”功能。

修复、升级与回退统一见 [部署维护](../deploy/README.md)。环境证据按日期、固定提交、ACK/实际可见/真实往返分层记录，参照 [人工清单](ACCEPTANCE.md)。
